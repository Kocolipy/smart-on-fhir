# Backend architecture

The full form of `backend/AGENTS.md`'s "Architecture constraints": each rule, the
test that holds it, and the reason.

- Spring Security owns authentication.
- Authentication state is stored in the HTTP session.
- Spring Session persists sessions in Redis.
- Login, CSRF and health endpoints, the Epic JWKS (`GET /api/auth/epic/jwks.json`, ADR 0012, D14), and Epic Login's three browser routes (`GET /api/auth/epic/launch`, `/authorize` and `/callback`, ADR 0012) are public — the Epic ones while Epic Login is on, and `404` while it is off; everything else on the application chain is deny-by-default (ADR 0015).
- **Every protected handler declares its Permission with method security** — `@PreAuthorize("hasAuthority('<permission>')")` on the handler method, nowhere else (or `hasRole('SUPERUSER')` for the Superuser-only operations: connector creation and deletion, the token operations, and setting a Group's Permissions, ADR 0015) — and the application chain repeats the same Permission as a URL rule, as a backstop. Its final rule denies whatever no earlier rule named, so a route left out of `SecurityConfig` is refused rather than open — with one recorded carve-out: any method but `GET` on `/api/patient/*` is admitted to a baseline (`ROLE_USER`) session so the dispatcher answers it `405` (no operation serves it), and a future patient write must put its own Permission rule ahead of that one (ADR 0015) — and a handler added without a declaration fails `ArchitectureTest.every_protected_handler_declares_a_permission`. Self-service handlers (`AuthController`, `SelfController`, and `EpicFhircastController`, the FHIRcast release of ADR 0016, ruled by `EpicLoginOn`) and the public `EpicJwksController` and `EpicLaunchController` need no Permission and are listed as such in both places. The SCIM (bearer) chain follows the same rule, with `ScimPermissionRule` as its backstop (ADR 0015); its token-only handlers, Discovery and `/Me`, are listed in `ArchitectureTest.TOKEN_ONLY_SCIM_CONTROLLERS`. A new operation therefore needs three things that agree: the handler's declaration, the chain's rule, and the `security` requirement in `docs/openapi.yaml` — `AuthorizationContractTests` proves the three against each other for every documented operation. The app-wide `ApiExceptionHandler` hands a method-security refusal back to the chain (it must never become a `500`), which answers, logs and audits it as the generic refusal.
- **Authority is DERIVED from Group membership, not stored.** Every active SCIM User receives baseline `ROLE_USER` (self-service only), and its Permissions are the baseline `patient:read` plus the union of the Group Permissions — stored per Group in `group_permission` — of the Groups it directly belongs to; a Group with none confers nothing. The Admin group, recognised by its reservation marker alone, carries none: a direct member is the Superuser (ADR 0015), whose session holds `ROLE_SUPERUSER` and every delegatable Permission, added in code at login.
- **Authority is derived once, at login.** A session carries the authorities it was issued with, so adding a User to a Group grants the Group's Permissions at its next login and never mid-session. That is the specified behaviour rather than a limitation: recomputing per request would make an authority change take effect at an unpredictable moment and would put a database read on every authenticated request. `ScimEndToEndIntegrationTests` pins both directions of it.
- The Admin group is resolved by its reservation marker (`scim_resources.reserved_name`), never by its `displayName`. A protection or a derivation that depended on an attribute a connector may change would be no protection at all — which is also why that column is not updatable, and why the Bootstrap Admin's lockout exemption reads the same marker.
- A credential never reaches a web adapter. The application layer hands out projections (`IdentitySummary`, `ScimUserResource`) that have no field a password hash could be written into, so exposure is prevented structurally rather than by review. `ArchitectureTest` holds the boundary, so a future handler cannot reach around the projection by taking the aggregate.
- The login path and the administration path do not share an application service. `LoginIdentityService` serves authentication (`UserDetails` and the derived authorities); `IdentityAdministrationService` serves an administrator and, of the two, is the only one that mutates an identity. Do not add identity writes to the former; the login state — the failure run and Lockout, the dormancy basis, the change-required flag, the completed password change — is written by the login-state module, `LoginStateService`, which the Login, password-change, Unlock and dormancy paths report to (`ArchitectureTest.only_the_login_state_module_writes_the_login_state`). It writes through a port of its own, `scim.domain.ScimLoginStateRepository`, apart from the directory's `ScimUserRepository`, and only `auth.application` — the module, and the dormancy job reading its lockout candidates — depends on that port (`ArchitectureTest.only_the_login_path_reaches_the_login_state_port`). Which columns each write of either port touches, and whether it advances the version, is held for the SQL Server adapter and the in-memory test store alike by `ScimUserRepositoryContract` and `ScimLoginStateRepositoryContract`. The directory reaches the same module through the `scim.domain.ScimUserLoginState` port it implements, so a SCIM create or replacement — a Reactivation by `PUT` or by `PATCH` alike — stores the login state the module decided, and `ScimUserRepository` and its queries store what they are given and decide nothing (`ArchitectureTest.the_directory_decides_no_login_state`). `LoginIdentityService` asks it nothing: whether a Login is confined comes from the module's own decision under the User's lock, which the Login hands it when it issues the session.
- **The login surface lives in `auth`; the directory lives in `scim`; the dependency runs one way.** `auth.application` reaches SCIM Users and Groups through `scim.domain` ports, and nothing in `scim` mentions `auth` — `ArchitectureTest.no_cyclic_dependencies` slices on `com.example.backend.(*)..`, so closing that loop fails the build. Anything needing a User's id from a userName goes through `ScimUserRepository`, not through the login surface's own service. `LockoutPolicy` lives in `scim.domain` for the same reason: the state it governs does.
- Authenticating submitted credentials goes through `LoginService`, which records the attempt against the identity as part of doing it. A web adapter never calls `AuthenticationManager` itself: an entry point that did would authenticate with no lockout, and nothing would fail. See `/docs/adr/0001-count-attempts-and-complete-every-login-on-the-login-path.md`.
- Deactivation and unlocking are separate capabilities and neither performs the other — see **Unlock** in `/CONTEXT.md` and the rules in `/docs/domain/authentication.md`. A User may be inactive, locked, both, or neither, and restoring one says nothing about the other. Deactivation is the directory's (SCIM) or a scheduled job's; the administration adapter exposes no write to any directory-owned field — `userName`, `displayName`, `active`, Group membership — and addresses Users by stable id. `AdminAccountControllerTests.noHandlerWritesADirectoryOwnedAttribute` holds that.
- A login-state or administrative write uses a narrow port operation, never a full-row write. A login-state transition is written as what it changed — `ScimLoginStateRepository#writeChange`, given the state read under the User's lock and the state decided, writes only the login-state columns that differ, never the credential — and the two writes that are not column diffs stay their own operations: `imposeLock`'s compare-and-set and `completePasswordChange`. The login path writes the User's row on every rejected attempt from a value it read at the start, so a full-row write would revert whatever an administrator or a connector changed in between — a password included — and would advance the SCIM version for a change no client can see. `ScimLoginStateRepository#writeChange` records both reasons, and `ScimLoginStateRepositoryContract` holds both stores to them.
- Every per-User **Session revocation** goes through `SessionRevocationService`, which defers to the commit, ends the sessions, and audits and logs under its cause (see `/docs/domain/sessions.md`). A new trigger calls that module with a `SessionRevocationCause`, and the directory reaches it through the `ScimUserSessions` port. Only the module calls the `AccountSessions` port. That port names one capability ("this account's sessions end"), and the `..infrastructure.session..` adapter owns everything Spring Session about it. `spring.session.data.redis.repository-type: indexed` is load-bearing: the default repository cannot be searched by principal, has no bean for that adapter, and startup fails rather than accepting a revocation it cannot enforce. It is set in `src/main/resources/session.yaml`, which the main and test `application.yaml` both import so they cannot disagree — change it there, not in either of them.
- Ending the **caller's own** session — Logout, the end of a session after a successful password change, and a Login that signed nobody in — goes through `auth.controller.SessionEnding` with a `SessionEnding.Reason`. It runs one sequence: the reason's record (Logout's fail-closed `LOGOUT` audit and `user-logout` line, before invalidation), the invalidation, the security-context clear, the session-cookie expiry, and `Clear-Site-Data` where the reason sends it (Logout only). A new way of ending the caller's session is a new `Reason`, not a handler that invalidates by hand; `ArchitectureTest.only_session_ending_ends_the_callers_session` and `only_session_ending_expires_the_session_cookie` hold that. The rule covers all of `auth..` and names two exceptions. `AbsoluteSessionLifetimeFilter` ends a session that outlived its policy before the chain loads it, records its own `session-end`, and expires no cookie because the same request may open the next session. `EpicLaunchController`'s accepted launch replaces the browser's session rather than ending it (ADR 0012, D9): it invalidates the old one and opens the Login's new one in the same response, so there is no cookie to expire; its refusals go through `SessionEnding`. Ending a User's **other** sessions is Session revocation, above.
- **A security-chain filter that reads the signed-in session is a web-layer bean, placed by name.** `AbsoluteSessionLifetimeFilter` and `SessionUserLogContextFilter` live in `auth.controller` as named `@Component`s. `SecurityConfig` injects each as a plain `jakarta.servlet.Filter` by `@Qualifier` and adds it beside `SecurityContextHolderFilter`, never naming the type, because `..config..` and `..controller..` are separate onion adapter layers. Each also has a `FilterRegistrationBean` with `setEnabled(false)`: Boot registers every `Filter` bean with the servlet container unless told not to, and there the filter would run outside the chain, after which its once-per-request marker would skip it inside. `SecurityConfigTests.eachSessionFilterRunsOnceInsideTheChainBesideTheContextLoaderAndNotInTheContainer` holds the position and the missing container registration. A request mark one layer sets and the other reads goes in `observability`, as `EndedSession` and `RequestActor` do, not in either adapter layer.
- Every read and write of the signed-in session's own attributes — the owner's stable id under the principal index, and the Epic tokens with their lifetime-bounded idle clamp — goes through `auth.domain.SignedInSession`. Callers ask it questions (`owner()`, `epicTokens`, `boundByLifetime`) rather than reading the attribute map, so a missing or malformed index identifies nobody everywhere, never a `500`. The module is plain domain code over `SignedInSession.Attributes`, which exactly two adapters implement by delegation, one per session API: the servlet `HttpSessionAttributes` in `auth.controller`, for the web handlers and the application chain's session filters alike, and the read-only `SpringSessionAttributes` in `auth.infrastructure.session` (`ArchitectureTest.the_signed_in_session_has_one_adapter_per_session_api`). A new reader adapts its session the same way rather than calling `getAttribute`.
- Runtime credentials and environment-specific settings remain external configuration.

`src/test/java/arch/ArchitectureTest.java` is the executable form of the structural boundaries: the module graph, onion layering, package placement, naming, constructor injection, JPA mapping, and package-cycle freedom. The module graph is an allowlist, `MODULE_DEPENDENCIES`: a new top-level package under `com.example.backend` fails the build until it has an entry there, and a new dependency between modules fails until it is added to the depending module's set — so declare the edge deliberately, in that map, rather than working around the rule. The onion model treats `..config..` as an inbound adapter: configuration may wire an application seam, but application and domain code never depend on configuration. Read it before reshaping packages or adding a layer.
